# Task Tracker API

A learning-project REST API for tracking tasks on a Kanban board, built with Python, FastAPI and Pydantic v2. It ships with a single-file vanilla-JavaScript frontend and a pytest suite.

This is a course exercise, not a production service. There is no authentication, no database, and no deployment configuration. Task data lives in an in-memory dictionary and is lost when the process stops.

**What it does**

- Full CRUD over tasks: create, list, fetch, partially update, delete.
- Filtering by `status` and `priority` on the list endpoint.
- A status transition state machine — not every status change is permitted.
- Interactive API docs generated by FastAPI at `/docs`.
- A drag-and-drop Kanban board that talks to the API.

**Endpoints**

| Method | Path | Success | Notes |
| --- | --- | --- | --- |
| `GET` | `/health` | 200 | Liveness only; checks no dependencies |
| `POST` | `/tasks` | 201 | Server assigns `id`, `created_at`, `updated_at` |
| `GET` | `/tasks` | 200 | Optional `?status=` and `?priority=` filters, ANDed |
| `GET` | `/tasks/{task_id}` | 200 | 404 if unknown |
| `PATCH` | `/tasks/{task_id}` | 200 | Partial update; 422 on an illegal status transition |
| `DELETE` | `/tasks/{task_id}` | 204 | Empty body; 404 if unknown |

**Task fields**

`id`, `title`, `description`, `status`, `priority`, `assignee`, `created_at`, `updated_at`.

`status` is one of `ToDo` (default), `InProgress`, `Done`. `priority` is one of `Low`, `Medium` (default), `High`. Casing matters on the wire.

## Prerequisites

- **Python 3.11** — what CI runs. The code requires 3.10 or newer because it uses `X | None` annotations that are evaluated at runtime. `[VERIFY]` The local `.venv` is 3.12.0 and the previous README claimed 3.9+; 3.9 will not work.
- **pip**
- **Docker** — optional, only for the container workflow in section 6.

No linter, formatter, or build step is configured. There is no npm dependency; the frontend is plain HTML/CSS/JS.

## Local setup

All commands are run from the repository root.

**Linux/macOS**

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

**Windows (PowerShell)**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

The virtual environment directory is `.venv` (note the leading dot); it is already listed in `.gitignore`.

`.env.example` exists and can be copied to `.env`, but `[VERIFY]` nothing in `app/` currently reads it — `python-dotenv` is installed but never imported, and the server port comes from the `--port` flag. Copying it is optional and has no effect today.

## Run the app locally

```bash
uvicorn app.main:app --reload --port 8000
```

- API: `http://localhost:8000`
- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`

If the virtual environment is not activated on Windows, prefix the command:

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

Quick check that it is up:

```bash
curl http://localhost:8000/health
```

```json
{
  "status": "ok",

}
```

### Serving the frontend

In a second terminal, with the API already running:

```bash
python -m http.server 5500 --directory frontend
```

Open `http://localhost:5500`.

**Port 5500 is not arbitrary.** `app/main.py` hardcodes a CORS allowlist of exactly four origins — `http://localhost:5500`, `http://127.0.0.1:5500`, `http://localhost:5173`, and `null` (for opening the file directly over `file://`). The frontend in turn hardcodes `http://localhost:8000` at each `fetch` call site. Serving from any other port fails CORS; both sides must be changed together.

## Run tests

```bash
pytest -v
```

18 tests in `tests/test_tasks.py`. A single file or a single test:

```bash
pytest -v tests/test_tasks.py
pytest -v tests/test_tasks.py::test_patch_invalid_transition_todo_to_done_returns_422
```

On Windows without the virtual environment activated:

```powershell
.venv\Scripts\python.exe -m pytest -v
```

An autouse fixture in `tests/conftest.py` clears the in-memory store before and after every test, so tests do not leak state into one another.

Two deprecation warnings are expected and do not indicate failure: Starlette asks for `httpx2` instead of `httpx` as the `TestClient` transport, and `HTTP_422_UNPROCESSABLE_ENTITY` is deprecated in favour of `HTTP_422_UNPROCESSABLE_CONTENT`. Both are upstream renames; the status code is still 422.

`tests/verify_a.py` is **not** collected by pytest. It is a standalone script of print-based `PASS`/`FAIL` checks over the Pydantic models, run directly:

```bash
python tests/verify_a.py
```

## Run with Docker

The `Dockerfile` is a multi-stage build for running the API in a container locally. It is not a deployment configuration — there is no orchestration, no reverse proxy, no hosting setup, and no production hardening.

```bash
docker build -t task-tracker:dev .
docker run -d --name tt-dev -p 8000:8000 task-tracker:dev
```

The API is then reachable at `http://localhost:8000` exactly as it is when run with uvicorn directly.

```bash
curl http://localhost:8000/health
```

Stop and remove the container:

```bash
docker rm -f tt-dev
```

**What the image does.** A builder stage installs `requirements.txt` into a virtualenv at `/opt/venv`; the runtime stage copies only that virtualenv and the `app/` package, so no build toolchain, tests, frontend, or `.env` reaches the final image. Both stages pin `python:3.11-slim`. The container runs as the non-root user `app` (uid 1000), exposes port 8000, and starts uvicorn **without** `--reload`. A `HEALTHCHECK` polls `/health` using only the standard library.

Storage is in-memory, so tasks created in the container disappear when it stops.

**Troubleshooting.** If `docker build` fails during `pip install` with `CERTIFICATE_VERIFY_FAILED`, a TLS-inspecting proxy or antivirus on the host is intercepting the connection to PyPI. The host trusts the interceptor's certificate but the container does not. Disabling HTTPS scanning for `pypi.org` and `files.pythonhosted.org` resolves it; injecting the interceptor's CA into the image is not committed here because it is machine-specific.

## CI workflow summary

`.github/workflows/ci.yml` defines a single workflow named **CI** with one job, `test`.

| | |
| --- | --- |
| **Triggers** | Every `push` (any branch), and `pull_request` targeting `main` |
| **Runner** | `ubuntu-latest` |
| **Python** | 3.11, via `actions/setup-python@v5` |
| **Install** | `python -m pip install --upgrade pip` then `pip install -r requirements.txt` |
| **Test** | `pytest -v` |

That is the whole pipeline. There is no lint step, no coverage reporting, no matrix across Python versions or operating systems, no Docker build, no artifact upload, and no deployment stage. A green run means the 18 tests passed on Python 3.11 on Linux.

## Project conventions and current limitations

### Conventions

- **Layering.** `storage.py` signals absence by return value (`None` / `False`) and never raises HTTP errors. `main.py` alone owns `HTTPException` and translates a miss into a 404. Adding an HTTP raise inside `storage.py` would break that split.
- **Business rules live in `business_rules.py`.** `VALID_TRANSITIONS` is a `frozenset` of exactly six `(from, to)` pairs; anything else is a 422 whose detail enumerates the permitted transitions.

  | from ↓ / to → | ToDo | InProgress | Done |
  | --- | --- | --- | --- |
  | **ToDo** | allowed | allowed | rejected |
  | **InProgress** | rejected | allowed | allowed |
  | **Done** | rejected | allowed | allowed |

  Self-transitions are explicitly permitted, so re-sending the current status returns 200. `ToDo → Done` is rejected: work must pass through `InProgress`. `Done → InProgress` reopens a task, but nothing may return to `ToDo` once it has left.
- **Validation order.** On PATCH, an unknown `task_id` yields 404 before any transition check — a nonexistent task never produces a 422.
- **`extra="forbid"` on every model,** so an unrecognized request field is a 422 rather than being silently ignored. This also prevents a client injecting `id` or `created_at`.
- **`title` is stripped, rejected when blank, and capped at 200 characters.** The validator is duplicated across `TaskCreate` and `TaskUpdate` because the update variant must pass `None` through untouched; keep the two in sync.
- **PATCH is genuinely partial.** Omitting a field leaves it alone, which is not the same as sending it as `null`. An empty body returns the task unchanged without advancing `updated_at`.
- **Server-owned fields.** `id` is a uuid4 string; `created_at` and `updated_at` are timezone-aware UTC and set in `storage.py`, never by the client.
- **Google-style docstrings** on public functions and route handlers.

### Limitations

- **Storage is in-memory, not file-based.** `storage.py` holds a module-level dict. Data does not survive a restart, and running more than one worker would give each its own copy. `[VERIFY]` The FastAPI `description=` string in `app/main.py` still advertises "file-based JSON storage" and is visible in Swagger UI; it is inaccurate.
- **No authentication or authorization.** Every endpoint is open. Out of scope by design.
- **No database and no ORM.**
- **Not production-ready and not deployed anywhere.** The Docker setup runs the app locally; it is not a deployment pipeline.
- **Dependencies are unpinned.** `requirements.txt` names packages without versions, so a fresh install can resolve different releases than the ones in `.venv` — a container build has already resolved a newer FastAPI and uvicorn than the local environment. Builds are therefore not reproducible.
- **`.env`, `.env.example` and `python-dotenv` are unused.** `[VERIFY]` Nothing reads `PORT` or `APP_ENV`.
- **CORS is a hardcoded four-origin allowlist,** and the frontend hardcodes the API URL. See "Serving the frontend".
- **Empty scaffolding directories remain** under `app/`. `app/models/` coexists with `app/models.py`, and `app/storage/` with `app/storage.py`. Imports resolve to the `.py` files today, but adding an `__init__.py` to either directory would shadow the real module.
- **No pagination, sorting, or search** on `GET /tasks`.
- **No linter or formatter** is configured.
- `[VERIFY]` **`PATCH` with an explicit `{"status": null}` bypasses transition validation** and writes a null status onto the stored task, which then persists and is served on later reads. This is an open defect, not intended behavior.
